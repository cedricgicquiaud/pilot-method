Pilotage de projet

Le circuit Linear · GitHub · Claude

Trois outils, trois rôles qui ne se recouvrent pas, et une seule règle qui les fait tenir ensemble.

1. Chacun son métier

Linear

Le tableau de bord. Roadmap, features, tâches, statuts. C'est l'écran que tu regardes.

Ne contient aucun code.

GitHub

L'atelier. Le code, les branches, les pull requests, les tests qui tournent.

Tu n'y vas que pour relire du code ou merger.

Claude

L'ouvrier. Lit la tâche dans Linear, écrit le code dans GitHub, ouvre la PR.

Ne merge jamais : c'est toi qui décides.

3. Les étages de Linear

GitHub range tout à plat. Linear empile, et c'est l'empilement qui donne une roadmap. Attention au vocabulaire de Linear : ce qu'il appelle « projet » est une feature du produit, pas le produit lui-même.

Trois règles gouvernent ce qui s'enchaîne. Les dépendances sont rares et réelles : on ne relie deux features que si inverser l'ordre casse — pas si c'est juste l'ordre prévu. La frise montre le scénario retenu : le plan auquel on croit reste daté, même derrière une décision pas encore prise ; l'autre branche attend en réserve, sans dates, et une alerte rappelle chaque session de retard de la décision. Les dates se recalent en racontant : Linear ne décale jamais rien tout seul ; c'est Claude qui replanifie à chaque session et ouvre par le récit — ce qui a glissé, et la marge restante avant la date butoir du projet.

4. Une feature, du début à la fin

Ce qui se passe réellement pour « Onboarding guidé » (trois écrans à la première connexion), et qui appuie sur le bouton à chaque étape.

  1. Toi
    Au cadrage du projet, je te propose la liste de toutes ses features, avec une taille (S, M, L, XL). Tu valides, je les pose sur la roadmap, statut « À cadrer », sans aucune tâche. « Onboarding guidé » en fait partie.
  2. Claude
    Quand son tour vient, on cadre la feature : les décisions produit, et surtout la liste de ce qui devra être vrai à la fin — dix à trente phrases observables, dont un tiers de refus (« un écran sans titre ne s'enregistre pas »). Un agent relit ce cadrage et te dit ce qui manque, sans proposer de solution. Tu valides.
  3. Claude
    Je découpe la feature en livraisons qui ne touchent pas les mêmes fichiers — c'est ce qui permettra de les produire séparément sans que les travaux se télescopent. Chaque phrase du cadrage est affectée à une livraison. Tu valides, je crée toutes les tâches d'un coup (ABC-21, ABC-22, ABC-23…) au moule : problème, action, terminé quand. La feature passe « Planifiée ».
  4. Agents
    La production, sans toi. Une copie du dépôt par livraison, et dedans un agent — un par tâche sur une grosse livraison. Il écrit d'abord le test qui échoue, puis le code minimal qui le fait réussir — un enregistrement par étape, pour qu'on puisse prouver après coup que le test précédait le code. À chaque tâche finie, elle passe en « Terminé » dans Linear et ta barre avance.
  5. Agents
    La vérification, par deux agents qui n'ont pas écrit le code. L'un relit les lignes changées et relance les tests lui-même : un rapport qui reprend les chiffres de celui qu'il contrôle ne prouve rien. L'autre ouvre l'application et regarde les écrans livrés. Jamais les deux à la fois — c'est ce qui fait deux preuves différentes. S'ils trouvent quelque chose, un troisième agent corrige la liste, une seule fois.
  6. Claude
    J'ouvre la PR sur GitHub, titre « ABC-21 Écran de bienvenue », avec le rapport d'audit : ce qui est prouvé, ce qu'il te reste à relire, et les décisions à trancher que les agents ont refusé de prendre en chemin. Dernière ligne : Closes ABC-21, ABC-22, ABC-23. Je passe la feature « En revue », et je m'arrête.
  7. GitHub → Linear
    Les tâches passent « En revue » dans Linear. Personne n'a rien fait : c'est l'intégration.
  8. Toi
    Tu relis la PR et tu merges. C'est aussi là que tu tranches les décisions remontées : sans ta réponse, la livraison suivante les devinerait.
  9. GitHub → Linear
    PR mergée : les trois tâches passent « Terminée », la livraison est finie, la barre de la feature avance. Livraison suivante, même circuit, jusqu'à 100 %. Automatique aussi.
  10. Claude
    À ma session suivante, je constate le merge et je passe la feature « Terminée ». Puis j'apprends : chaque défaut trouvé à l'audit devient une règle écrite dans le CLAUDE.md du dépôt, que la livraison suivante appliquera. Les décisions que tu as tranchées sont gravées dans la fiche. Les idées apparues en chemin deviennent des tâches sans feature. Puis je prends la feature suivante.

5. La seule règle

Le code de la tâche voyage dans le nom de la branche et le titre de la PR. C'est ce qui permet à Linear de reconnaître ses tâches dans ce que fait GitHub, et de les faire avancer sans que personne n'y touche — les tâches seulement : le statut d'une feature, c'est Claude qui le pose. Et rien n'est créé dans Linear sans ta validation. Sans ce code, les deux outils ne se reconnaissent pas et tu retombes sur deux listes à tenir à la main.

Ce qui ne s'automatise pas, par choix : ta décision de merger, et l'ordre des features sur la roadmap. Le reste suit.
